# Trayecto AVE 2026-06-01 — validación v1 vs v2 ubond

Sesión de validación end-to-end de v2.0.0 (ubond) contra v1.0.0
(mlvpn) en condiciones reales del AVE Madrid→Orihuela.

## Resumen ejecutivo

**v2 ubond + per-link tolerences (REQ-NET-25) es claramente
superior a v1 mlvpn `--failover` en el AVE.** Diferencias medidas:

- Latencia: ~60× mejor (3991ms → 69ms ping 1.1.1.1).
- Throughput: ~4× mejor (314 → 1316 KB/s en descarga 1MB).
- Loss: 20% → 0% paquetes ICMP.

Sin tolerences custom, v2 ya mejora v1 en latencia (83ms vs 3991ms)
pero NO en throughput. Las tolerences cambian el juego.

## Configuración del trayecto

- **Mac**: M3 Pro, macOS 25.4. Binario ubond `/usr/local/sbin/ubond`
  con REQ-NET-12 + REQ-NET-19 + REQ-NET-25 patches aplicados.
- **RPi**: 200bares.dedyn.io (170.253.45.213). Binario ubond con
  los mismos patches. mlvpn.service y ubond.service ambos active.
- **Móviles**: iPhone 12 Movistar (en8, 172.20.10.4) + Pixel 6 Pro
  Yoigo (en12, 10.215.43.50) — ambos por USB tethering.
- **WiFi AVE** (en0, 172.18.153.67) — operador interno del tren,
  **sin captive portal**, latencia variable 100-1500ms.

## Fase 1 — v1 mlvpn `--failover` (baseline)

Comando: `sudo -A -E ./04-conectar.sh --failover`

```text
ping 10.10.10.1 ×20 :  18/20 (10% loss), avg 967ms (60-2238ms)
ping 1.1.1.1 ×20    :  16/20 (20% loss), avg 3991ms
IP pública vía túnel:  170.253.45.213 ✓ (RPi casa)
Throughput 1MB Cloudflare: 314 KB/s
Loss cycling syslog:   limpio
```

**Bug colateral identificado durante Fase 1:** la detección de
`UTUN_IFACE` en `04-conectar.sh:437` (regex
`grep -B1 "nd6 options" | grep "utun" | tail -1 | cut -d: -f1`)
es frágil en macOS modernos — devuelve `inet6 fe80` (texto del
ifconfig output mal parseado) en lugar de `utunN`. Resultado:
mlvpn autentica pero el utun no se configura, las rutas /1 no
se añaden y el tráfico sale por la ruta default del operador
(NO por el túnel). Workaround manual aplicado en sesión:
detectar el utun via `lsof -p $MLVPN_WORKER_PID | grep utun_control`
para extraer el unit number y derivar `utun(N-1)`. Fix permanente
pendiente — replicar el snapshot before/after que ya implementé en
`04b-conectar-ubond.sh` esta sesión.

## Fase 2 — v2 ubond bonding (defaults, sin tolerences)

Comando: `sudo -A -E ./04b-conectar-ubond.sh`

```text
ping 10.10.20.1 ×20 :  17/20 (15% loss), avg 1135ms
ping 1.1.1.1 ×20    :  20/20 (0% loss), avg 83ms (jitter 16ms)
IP pública vía túnel:  170.253.45.213 ✓
Throughput 1MB      :  218 KB/s
Loss cycling syslog :  limpio
```

**Hallazgo:** v2 ya mejora v1 en latencia (83ms vs 3991ms a 1.1.1.1)
SIN tolerences custom. Pero el throughput es algo peor (218 vs 314)
y el process title muestra `~links.iphone` (lossy/transición), lo
que confirma que el threshold de keepalive ack (0.5s+2*RTT) está
agresivo para AVE.

## Fase 3 — v2 ubond + per-link tolerences (REQ-NET-25)

Conf: `[links.iphone]` y `[links.pixel]` con
`loss_tolerence = 80` y `latency_tolerence = 2000`.

Comando: `sudo -A -E ./04b-conectar-ubond.sh` (con conf editada).

```text
ping 10.10.20.1 ×20 :  20/20 (0% loss), avg 60ms (45-87ms)
ping 1.1.1.1 ×20    :  20/20 (0% loss), avg 69ms (54-85ms)
IP pública vía túnel:  170.253.45.213 ✓
Throughput 1MB      :  1316 KB/s
Loss cycling syslog :  limpio
Process title       :  @links.pixel @links.iphone (ambos AUTH OK)
```

**Mejora dramática vs Fase 2:** iPhone pasó de `~links.iphone`
(lossy) a `@links.iphone` (auth OK). El threshold relajado evita
el cycling y las tolerences per-link son la palanca correcta.

**WiFi del AVE** (`!links.wifi`) no autentica con UDP 5085 — el
operador del tren filtra puertos altos. Esperado.

## Veredicto

| Métrica | v1 Fase 1 | v2 Fase 2 | v2 Fase 3 |
|---------|-----------|-----------|------------|
| ping gateway loss | 10% | 15% | **0%** |
| ping gateway avg | 967ms | 1135ms | **60ms** |
| ping 1.1.1.1 loss | 20% | 0% | **0%** |
| ping 1.1.1.1 avg | 3991ms | 83ms | **69ms** |
| Throughput | 314 KB/s | 218 KB/s | **1316 KB/s** |

**v2 + tolerences gana en TODAS las métricas.** REQ-NET-25 valida
la hipótesis de Bug #6: el cycling tight de keepalive era la causa
del throughput colapsado. Con `latency_tolerence=2000ms` el
threshold sube a ~2.5s + 2*RTT, y los enlaces aguantan el jitter
del AVE.

## Fase 4 — replicación selectiva (NO completada, observación importante)

Tras Fase 3 se activó `[filters.replicate]` con reglas para
`api.anthropic.com`, `claude.ai`, `meet/zoom STUN/TURN` y
`rtp_generic`. ubond arrancó y autenticó al menos un enlace.

**Pero v2+replicación cayó dos veces durante la fase observación**:

- 1er intento: tras configurar utun y arrancar monitor periódico,
  el usuario reportó "sin red, he tirado del SOS.sh" pasados ~10
  min. SOS.sh restauró conectividad.
- 2º intento: tras pre-resolver IPs y relanzar 04b, la red volvió
  a caer al cabo de pocos minutos. SOS.sh otra vez.

Patrón observable: con replicación selectiva ACTIVA, los flaps de
cobertura (iPhone Movistar oscilando entre `@` y `~`/`!`) parecen
provocar pérdida total de conectividad por el túnel — más allá del
loss cycling de Bug #6 que ya está atenuado.

Hipótesis no validadas:

- La replicación duplica paquetes hacia un enlace que está cayendo,
  saturándolo y empujando ubond a estado inestable.
- El watcher de selección de mejor enlace
  (`tools/seleccionar-mejor-enlace.sh`) interactúa mal con la
  replicación cuando un link entra en `~`.
- Bug en el dedup LRU del receptor cuando la cobertura de un enlace
  oscila rápido (paquetes resend duplicados en ventanas de tiempo
  cortas).

**No se completaron tests de Fase 4** (curl Anthropic con/sin
replicación) por las caídas. Pendiente investigar en condiciones
controladas. Para uso real en AVE sin más debug, recomendable
desactivar la replicación selectiva.

Los scripts del repo en commit del día reproducen este test salvo:

- Hay que tener iPhone+Pixel tethered por USB.
- Hay que configurar tolerences manualmente o re-correr 03b
  para que el template tenga los ejemplos.
- El bug del utun detector se sortea con el lsof manual o el
  fix snapshot ya commiteado en 04b.
