## Bugs descubiertos y arreglados en vivo

### 1. SOS.sh roto (commit `beb561e`)

- `pkill -9 mlvpn` (sin `-f`) no encontraba procesos porque mlvpn
  cambia su `setproctitle` a `mlvpn: mlvpn0 [priv]`.
- `ping -W 3` en macOS son **3 milisegundos**, no segundos (sintaxis
  Linux). La verificación final siempre fallaba aunque hubiera
  internet.
- No mataba watchers (selector, calibrador, wifi-watcher).
- Borraba TODAS las `/32` con `netstat | awk` — peligroso para rutas
  legítimas (NAS, impresoras).
- No se auto-relanzaba con sudo.

Reescrito con todas estas correcciones + auto-relaunch + path
absoluto.

### 2. Reintegrador WiFi tras captive (REQ-NET-13, commit `beb561e`)

Caso real: subes al AVE, conectas WiFi (IP pero captive sin auth),
lanzas `04-conectar.sh` → captive falla → WiFi descartada
**permanentemente** hasta reconectar todo. Después autenticas el
captive en navegador → la WiFi pasa a ser usable, pero el túnel nunca
la evalúa de nuevo.

`tools/wifi-reintegrator.sh` arranca cuando WiFi tiene IP pero no
pasó pre-flight. Cada 30 s reintenta y, cuando pasa, añade
`[links.wifi]` dinámicamente al `mlvpn_active.conf` + `SIGHUP` a
mlvpn.

### 3. Selector no rotaba con activo en `!` (REQ-NET-14, commit `ecb466b`)

Caso real: `iPhone` configurado como activo (sin `fallback_only`)
pero mlvpn lo tenía en `!` AUTH_PENDING (UDP filtrado o operador
caído); `Pixel` sí en `@`. El selector veía iPhone como
`current_active` aunque no estuviera autenticado a nivel mlvpn.
Esperaba al gap≥20 puntos antes de rotar — segundos perdidos en
cada arranque.

Fix: si `current_active_link` ∉ `authenticated_links()`, rotación
inmediata sin gap.

**Verificado en vivo durante el trayecto**: tras commit `ecb466b`,
vi en el config que el selector había rotado iPhone (`fallback=1`)
↔ Pixel (`fallback=0`) automáticamente.

### 4. Detección de flapping (REQ-NET-15, commit `ecb466b`)

Caso real: el WiFi del AVE oscila entre `@` y `!` cada pocos
segundos: handshake mlvpn (UDP pequeño) atraviesa el firewall →
empieza a fluir tráfico → DPI/firewall corta UDP → `!` → reintento
→ ciclo. ICMP responde (los pings pasan), pero el túnel UDP no.

Sin tratamiento, gasta CPU + datos en re-handshakes inútiles. El
selector ahora cuenta transiciones `@↔!` en ventana de 60 s. Si
superan 4, marca el link como flapping y lo excluye del pool. Cuando
el link recupera y está `@` estable durante 30 s, se reintegra.

### 5. Bash 3.2 vs `declare -A` (commit `f162459`)

Los nuevos watchers usan arrays asociativos (`declare -A`),
incompatibles con bash 3.2 que es lo que macOS instala en
`/bin/bash`. El selector arrancado por sudo moría inmediatamente
con `line 44: iphone: unbound variable`.

Fix: cada script con `declare -A` comprueba `BASH_VERSINFO[0]` al
inicio y, si <4, hace `exec` a `/opt/homebrew/bin/bash` o
`/usr/local/bin/bash`. Sin Homebrew bash disponible, falla con
mensaje claro. **Lección IDLC**: validar prerequisites de runtime al
arrancar, no asumir.

### 6. Predicado de log incorrecto (commit `0202531`)

`log show --predicate 'process == "mlvpn-selector"'` no encuentra
nada en macOS. El comando `logger -t TAG "msg"` aparece en Apple
Unified Log con `process == "logger"` y el TAG dentro del
`eventMessage`. El predicado correcto es:

```
log stream --predicate 'eventMessage CONTAINS "mlvpn-selector"' --info
```

Actualizado README, REQ-NET-11 doc.

### 7. Reintegrador no heredaba `--failover` (commit `0202531`)

Cuando el `wifi-reintegrator` añadía `[links.wifi]` tras autenticar
captive, NO le ponía `fallback_only=1` aunque el túnel estuviera en
`--failover`. Eso rompía momentáneamente el modelo "1 activo, demás
backup" hasta que el selector rotara.

Fix: el reintegrator detecta si algún otro link tiene
`fallback_only=1` en `mlvpn_active.conf`. Si sí, marca el WiFi
también como fallback al añadirlo.

## Bugs detectados pero NO arreglados (siguiente sesión)

### Selector mide solo ping, no throughput

Caso visto 2026-05-22 y 2026-05-25: enlaces que responden al ping
ICMP (`@` autenticado, RTT bajo) pero con throughput **0 KB/s** real.
El selector elige uno de esos como ganador y rompe el túnel.

Mitigaciones discutidas:

- A. Curl 1 MB cada 30 s — descartado: 200 MB/h, demasiado caro.
- B. Curl 100 KB cada 5 min — más razonable: ~12 MB/h.
- C. Aprovechar contadores `netstat -ibn` por interfaz para detectar
  "ping responde pero counter no crece" — solo si hay tráfico real
  fluyendo (asunción frágil).

Decisión pendiente para próxima sesión.

### Monitor `08-monitor.py` agregando en `--failover`

El usuario observó en el AVE que el monitor mostraba tráfico en
ambos móviles aunque el modo era `--failover` (donde solo el activo
debe llevar carga, los `fallback_only=1` solo keepalives). Sin
medición concreta de deltas durante una descarga, no se confirmó si:

- (a) El monitor lee counters físicos sin distinguir activo/fallback
  (esperado: muestra suma incluyendo keepalives).
- (b) `mlvpn` realmente está enviando data por el fallback (bug en
  el comportamiento de `fallback_only`).

Sin datos concretos, hipótesis (a) más probable. Pendiente medir
deltas pre/post descarga para confirmar.

### Captive portal pre-flight con `curl --interface`

En pruebas en casa el `curl --interface en0` daba timeout aunque la
WiFi tenía internet. En el AVE durante el trayecto SÍ funcionó
(captive autenticado, `curl --interface en0` devolvía
`<TITLE>Success</TITLE>`). El comportamiento es inconsistente entre
escenarios — necesita más datos.

## Comportamiento observado del bonding paquete-a-paquete

Sin `--failover`, en el primer arranque del trayecto:
- Throughput colapsado: 80 KB/s (vs 4 MB/s del iPhone solo)
- Conexiones HTTP/2 (Anthropic API streaming) inutilizables
- `curl` con descarga lineal sí funcionaba (~3 MB/s aislado)

Esto **valida en producción** la hipótesis de los REQ-NET-09/10/11:
el bonding paquete-a-paquete no funciona para sesiones
interactivas con enlaces de latencias dispares. El `--failover`
dinámico es la solución para uso real.

## Decisiones para v2.0.0 — confirmadas tras este trayecto

1. **El selector debe medir throughput**, no solo ping. Punto crítico
   para el roadmap.
2. **El monitor 08-monitor.py necesita un modo `--failover-aware`**
   que muestre activo vs backup distinto.
3. **Documentación clara del bash 4+ requerido** para todo el flujo
   de watchers — añadir a `tests/verificar-setup.sh` un check
   inicial.
